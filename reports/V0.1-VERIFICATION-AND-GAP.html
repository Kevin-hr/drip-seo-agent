对你上传的 drip-chatgpt-seo-plugin-v0.1.0.zip 逐项实测，并勘察你现有本地 Agent（dripops）后得出的可交付结论。

0. 一句话结论

插件本体是真的、且比我原以为的更可信：ZIP 哈希与声明完全一致，12 个 MCP Tool 在真实 MCP 客户端下全部注册成功，SKU 硬门禁和 SSRF 防护实测有效。

但“把现有本地 Agent 接到 11 条 route”这件事，按你描述的形态做不了。原因不是代码写得不好，而是三个前提在本地根本不存在：本地没有 HTTP 服务、本地引擎实现的是 3.2 而非 V4.4、并且 3.2 强制要求 SKU 与 V4.4 的 SKU 省略规则互斥。另外我还实测出一个真实的 TypeScript 编译错误——这一项上个环境因为跑不了 typecheck 而漏掉了。

2. P0 级问题（必须先解决，否则集成毫无意义）

P0-1　插件当前编译不通过 已复现

这是上个环境没跑到的那一步，我跑完了，结果是失败：

> tsc --noEmit
src/validation.ts(17,74): error TS18047: 'input.sku' is possibly 'null'.

根因在 src/validation.ts 第 17 行：

if (input.sku && forbiddenSkuPatterns.some((pattern) => pattern.test(input.sku.trim()))) {

箭头函数闭包内再次访问 input.sku，TypeScript 的类型收窄不会跨越闭包边界生效，因此 input.sku 仍被视为 string | null。

为什么 npm test 却是 3/3 通过：测试跑在 tsx 上，tsx 只做类型擦除、不做类型检查。所以“测试通过”目前无法证明代码可编译。这也解释了为什么两个信号会互相矛盾。

修法（一行）：

const sku = input.sku?.trim();
if (sku && forbiddenSkuPatterns.some((pattern) => pattern.test(sku))) {

P0-2　插件里的 V4.4 不是生产用的那一版 严重

两个文件都叫 “V4.4 STANDARD — FINAL”，但它们是两份不同的文档：

文件SHA-256字节 / 行用途
Drip_Sneakers_SEO-PDP_V4.4_STANDARD_FINAL.md 965314CD…B34D3E5B7 19,351 / 1,031 生产跑批实际使用
Drip_Sneakers_SEO-PDP_V4.4_CLEAN_CONSOLIDATED_2026-09-17.md 5FB8457F…F3BF8 23,567 / 1,136 被插件打包

你的生产记录写得很明确——FINAL-REPORT.md 与 PROGRESS.md 都声明：唯一 SEO 标准是 965314CD…B34D3E5B7。而插件 rules/ 与 skills/…/references/ 里打包的是 5FB8457F…F3BF8。

两份文档的实质差异，已经能定位到以下章节：

  • CONSOLIDATED 多出 §5A Sample / Unreleased / Friends & Family Rule（生产版没有）
  • CONSOLIDATED 的 §10 多出 New / launch-stage PDP 与 Existing live PDP — stability rule 两个子节
  • §15 标题从 Mandatory Brand Internal Link 改成 Mandatory Verified Internal Link（判据口径不同）

影响：“byte-level 一致性检查”本身为真，但检查的是“插件内部两处副本是否一致”，并不等于“插件里的 V4.4 就是生产用的 V4.4”。这一项如果不裁决，ChatGPT 会拿着一份未经生产验证的标准去判 SKU 与实体，和 106 款已上架商品的判据不是同一套。

P0-3　本地没有可寻址的 Agent，11 条 route 没有宿主 阻塞

插件契约把 LOCAL_AGENT_BASE_URL 指向 127.0.0.1:8787，隐含前提是“本地已有一个 HTTP 服务”。实测你现有本地 Agent 没有任何 HTTP 层：

# 在 dripops 全部 C# 源码中检索 HTTP 服务关键字
HttpListener|WebApplication|Kestrel|UseUrls|ListenAsync|HttpServer
→ 命中数 = 0

# DripOps.csproj
<OutputType>Exe</OutputType>   <TargetFramework>net8.0</TargetFramework>
→ 纯控制台程序，未引用 ASP.NET

而且 MrshopplusClient.cs 并不是在调用 MrShopPlus 的 REST API，而是通过 Chrome DevTools Protocol 操作真实后台 DOM：

MrshopplusClient.cs:409  await _page.SendAsync("Input.dispatchKeyEvent", new
MrshopplusClient.cs:417  await _page.SendAsync("Input.dispatchKeyEvent", new

这意味着两件事：第一，不可能靠设置 AGENT_*_PATH 环境变量完成对接，必须新写一个 HTTP adapter；第二，这个 adapter 不是无状态包装器——它必须复用 ChromeController 并依赖一个已登录的持久 Chrome Profile，否则任何一次 write 都会在登录页停住。

P0-4　本地标准是 3.2 且强制要求 SKU，与插件的 SKU 省略规则互斥 架构冲突

插件与 V4.4 明确支持 SKU_OMIT——无 SKU 也能正常发布（106 款里有多款就是 (SKU omitted) 上线的）。但你本地唯一的确定性生成器/校验器不允许无 SKU：

影响：即便你现在就把 HTTP adapter 写出来，prepare-v44 也无处可调。这是三个阻塞项里最深的一个。

3. P1 级问题（不阻塞，但应修）

P1-1　图片 SSRF 检查存在 TOCTOU（DNS rebinding）

assertSafeExternalUrl() 先用 lookup(host, {all:true}) 解析并校验 IP，随后 fetch(url) 会再解析一次 DNS。校验与实际连接不是同一个地址，理论上可被 DNS rebinding 绕过。

另外 isPrivateIpv6() 只覆盖 ::1 / :: / fc* / fd* / fe80:*，未覆盖 IPv4-mapped IPv6（如 ::ffff:127.0.0.1）。实测该 URL 确实被挡下，但拦截原因是 fetch failed（DNS 解析失败）而非规则命中——属于侥幸拦截。

未覆盖的网段还包括 CGNAT 100.64/10、198.18/15、192.0.2/24、198.51.100/24、203.0.113/24。

建议：你的真实图片只来自 images.mrshopplus.com（已实测确认，见 §4），因此最稳的修法是域名白名单，把“通用 SSRF 防护”简化成“只允许一个已知图床”，风险面直接归零。

P1-2　mcp.json 仍是占位符

"url": "https://REPLACE-WITH-YOUR-MCP-HOST.example.com/mcp"

这是预期内的待办，但请注意：它意味着当前 ZIP 不能直接注册到 ChatGPT，必须先有公网 HTTPS 端点（或用 Secure MCP Tunnel 做开发态）。

P1-3　get_product_images 未声明 outputSchema

其余 11 个工具都声明了 outputSchema，只有它没有，但仍然返回 structuredContent。当前 MCP SDK 允许（不校验），但与其余工具口径不齐，建议补齐以便客户端一致性校验。

4. 11 条 Bridge Route 的真实映射现状

我把契约逐条对照了你本地实际存在的能力（dripops CLI + data/runs 状态 + .codex 脚本），结论如下。“可复用”一栏是逐条核实过的，不是推测。

Route契约要求本地现状判定
/products/search 按 ID / 名称 / 状态检索商品，只读 无等价能力。DripOps scan 只能按分类页扫描，不能按关键字/ID 反查 需新建
/products/read 返回完整商品快照（名称/图片/URL/状态/当前 SEO/供应商/本地证据） 可复用：DripOps snapshot + data/runs/RUN/products/PID.json。其 snapshot.imageUrls 已是公开 HTTPS 图床（实测 14 张，形如 https://images.mrshopplus.com/…/chrome_hearts_t_shirt_1E3165B42D518.jpeg），天然满足 get_product_images 的取图路径 可直接映射
/products/prepare-v44 消费 ChatGPT 的实体/SKU 判定，跑本地 V4.4 生成+校验，产出不可变 plan_id，不写库 不存在。本地唯一的生成/校验器是 3.2（SeoPdpComposer / SeoPdpValidator）。V4.4 生成器从未落地为代码，106 款是 .codex 一次性脚本跑的，且 V4.4 允许无 SKU 而 3.2 禁止 缺失且冲突
/products/execute-v44 只接受 product_id + plan_id，复检身份/版本/哈希后走 saveModify + 上架 部分可复用：DripOps apply --publish / publish-saved 已实现保存+上架。但没有 plan_id 概念——现有闸门是 ReleaseStatus = Ready，不是不可变计划对象，需新增 需加 plan_id 层
/products/verify-v44 后台回读 + 前台验收（HTTP 200 / SEO Title / H1 / canonical / meta / Key Description 5 li / 图片 ALT / Schema / IsShow / sitemap） 可复用：DripOps verify-frontend（HTTP、H1、Meta、Canonical、noindex、JSON-LD）+ apply 内置的保存后后台回读 可映射（需补字段）
/categories/search 检索分类/集合页 弱。DripOps find-category 只做单次定位，无列表检索 基本需新建
/categories/read 读分类页当前字段与 SEO 上下文 无。分类页 SEO 在你的本地链路里没有专门实现 需新建
/categories/prepare-seo 分类页 SEO dry run，产出 plan_id，禁止套用 PDP 字段 无 需新建
/categories/execute-seo 应用不可变分类 SEO 计划 无 需新建
/categories/verify-seo 分类页验收 无 需新建
/runs/status 返回持久化批次进度与断点 可复用：DripOps status --run + data/runs/RUN_ID/run.json + 每商品 checkpoint + events.jsonl 可直接映射

汇总：11 条 route 中，2 条可直接映射（products/read、runs/status），2 条可在加一层 plan_id 后复用（execute-v44、verify-v44），7 条需新建——其中 prepare-v44 卡在 P0-4 的标准冲突上，4 条分类页 route 本地是完全空缺。

7. 建议的下一步

真实瓶颈不在 MCP 层，而在“本地到底以哪套标准、哪个进程、哪份代码为准”。在你裁决之前写 adapter 是无效投入。建议按顺序做三件事：

  1. 先定标准（半天内可完成）。决定本地权威标准是 3.2 还是 V4.4，并把 dripops/standards、SeoPdpComposer、SeoPdpValidator 与插件 rules/ 统一到同一份文件与同一个哈希。这一步决定后面所有事。
  2. 再定 SKU 语义。确认 SKU_OMIT 是否合法。若合法，3.2 的 requiredVerifiedFacts 与校验器的 FACT-02 必须放宽；若不合法，插件的 SKU_OMIT 分支与 sku=null 契约必须收紧。
  3. 最后写 adapter。在 dripops 内加一个 serve 子命令，复用 ChromeController 与已登录 Profile，落地 11 条 route 中的可映射项，并为 write 路径补上真正的 plan_id（当前只有 ReleaseStatus=Ready，不满足“不可变计划”要求）。

另外建议顺手做的两件小事：修掉 P0-1 那一行编译错误；把图片抓取从“通用 SSRF 防护”收敛为 images.mrshopplus.com 白名单。
