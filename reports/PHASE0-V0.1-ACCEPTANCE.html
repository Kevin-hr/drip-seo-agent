不是靠代码审阅声称，而是靠**目录树逐字节哈希对比**证明：

const beforeTree = hashTree(state/runs);          // 遍历 230 个检查点，逐个算 sha256
await prepare(...);                                // SKU_OMIT 与 VERIFIED_SKU 各一次
const afterTree  = hashTree(state/runs);
beforeTree === afterTree                           → true

PASS  prepare.no_write_to_shop_state :: state/runs tree unchanged (byte-identical)
PASS  prepare.plan_persisted_immutably :: 1 plan file(s)
PASS  prepare.mrshopplus_not_contacted :: no execution recorded

为了让这条性质成立，我修掉了一个自己写出来的问题：prepare 最初复用 RunStore.AppendEvent，会把审计事件追加进 data/runs/{run}/events.jsonl，从而改动 run 目录。现在 Bridge 的审计一律写在 data/bridge/events.jsonl，shop 运行状态只由真实写入动作改动。

另一层结构性保证：prepare 的默认路径（live=false）不引用 ChromeController 与 MrshopplusClient，只读本地检查点；只有显式传 live=true 才会走一次只读快照。也就是说 prepare 在代码路径上就没有可写后端的能力。

攻击方式期望实测

直接注入 SEO 字段
seo_title/meta_description/slug		字段被忽略200，但标题仍是 plan 的标题，slug 未变成 injected-slug

plan 文件本身是不可变的：写入后只允许追加「已执行」与「已验证」两个状态，草稿、standard_hash、snapshot_hash、validation_status 一旦被改动就会抛 Plan immutability violated。execute 只接受 product_id + plan_id——「任意 SEO 字段直写」在这个接口上无法表达，这是结构性的，不依赖模型自觉。

为什么我没有跑 live 写入

环境上是具备条件的：Chrome 已安装，dist/data/chrome-profile 存在，DripOps self-test 也通过（说明我改动 Program.cs / 配置后原有 CLI 无回归）。

但 不能跑，原因是内容问题而非技术问题：为了做端到端测试，我构造的 v44_facts 是我编的——"Chrome Hearts T-Shirt Black"、"Cross Logo Front Print"、以及一个我推测的 Brand 内链。目标商品 536027552331542 是**你在售的真实商品**。一旦 live 执行，它会带着这些未经核实的虚构事实被保存并上架，直接违反 V4.4 §0「Do not optimize the wrong product」和 §9 的 unsupported-claim guard，也违反本仓库自己的红线。

要跑 live，需要你提供（或让 ChatGPT 研究出）以下已核实内容：

  • 该商品锁定的 exact entity 与官方 colorway
  • 若用 SKU：Tier 1–4 来源且 SKU 全等的证据
  • 若用 SKU_OMIT：一句基于实际商品的 decision sentence + 第五字段的已验证产品事实
  • 真实存在的、可访问的 Brand 分类内链
  • 一个明确指定要处理的目标 Product ID

给我这五项，我就能跑真正的单商品 live execute + verify 并给出前后台证据。或者你也可以先用 --mode live 自己跑一次，我按你的做法补证据。

J. 仍存在的 blocker

J1　dist/ 还没重新构建

我只做了 dotnet build（输出到 src/DripOps/bin/）。dist/DripOps.exe 里还没有 Bridge，也还没有 V4.4 标准文件。要生成可用可执行文件，请跑一次 .\build.ps1（我已把两个 V4.4 文件加进它的复制清单）。

J2　ChatGPT 还连不上

mcp.json 仍是占位符 https://REPLACE-WITH-YOUR-MCP-HOST.example.com/mcp。需要一个公网 HTTPS 端点，或开发阶段用 Secure MCP Tunnel。这不是代码问题，是部署步骤。

J3　分类页 5 条 route 没有实现

按你的要求暂缓：插件侧保留工具声明，但 Bridge 侧没有对应路由实现，调用会得到 404。PDP 证明完之后再扩。

J4　V4.4 校验器覆盖的是可机器判定子集

已实现的是确定性可判定的部分（模板全等、5 字段计数、Brand 内链、性别/供应商标记、URL 规则、Schema、三态 SKU）。不可机器判定的部分仍需 ChatGPT 的视觉判断——例如「主图是否真的匹配所声称的配色」「前后印花描述是否属实」。Bridge 会在 ALT 过于通用时给出 ALT-02 WARN，但不会假装自己能看图。这是设计边界，不是遗漏。

J5　3.2 CLI 命令仍在仓库里

按你的裁决，3.2 不再作为决策层，保留它只是为了不破坏你已有的 CLI。我额外做了一道硬隔离：Bridge 在加载 3.2 机器标准之前就被路由，所以它在代码路径上无法读取 3.2 规则。但 3.2 的 compose/apply 命令本身仍可被手动调用——如果你希望彻底停用，我可以把它们改成显式报错。
